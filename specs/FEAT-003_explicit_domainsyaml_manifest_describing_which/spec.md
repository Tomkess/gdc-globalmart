## Summary

The predecessor decided domain membership at split time by testing whether a visualization's id
started with `viz_<domain>_`, and it included a dashboard only if **all** of its visualizations
matched. A dashboard mixing Sales and Finance tiles therefore matched no domain and was silently
dropped — no error, no report, no count. The domain list itself lived in four places (the splitter,
the publisher, the workspace-creation script and a hand-maintained README table), so adding a domain
meant four edits and forgetting one was invisible.

FEAT-003 replaces that with a single declarative file, `config/domains.yaml`: the one place in the
repo that says which dashboards, which visualizations and which AI-context objects belong to each of
the 12 domains, what each child workspace is called, and what is *deliberately* in no domain and
why. It ships three things — the file, a strict loader/validator that fails loudly when the parent
and the manifest disagree, and a one-time bootstrap generator that uses the `viz_<domain>_` prefix
convention exactly once to produce the first version of the file for human review. From then on the
prefix is dead: membership is read, never inferred.

Nothing here splits, prunes or publishes anything. FEAT-004 consumes this manifest; FEAT-003 owns it.

`s` — 1–3 days

## Acceptance Criteria

- [ ] Given `config/domains.yaml`, when it is loaded with `load_domains()`, then a `DomainManifest`
      is returned carrying 12 `Domain` entries with snake_case keys `sales`, `ecommerce`, `product`,
      `customer`, `loyalty`, `inventory`, `marketing`, `finance`, `store_ops`, `hr`, `risk`,
      `real_estate`, each with a non-empty label, a child workspace id and an explicit dashboard list.
- [ ] Given the parent tree at `layouts/workspaces/globalmart/` and the manifest, when
      `globalmart domains validate` runs, then every one of the 32 analytical dashboards and every
      one of the 384 visualization objects is either assigned to at least one domain, listed under
      `shared:`, or listed under `unassigned:` with a non-empty `reason`; any object in none of the
      three fails the command with exit code 1 and the offending ids printed.
- [ ] Given a dashboard whose visualizations span two domains (the case the predecessor dropped),
      when it is listed under both domain keys, then validation passes, the coverage report marks it
      `multi-homed: [sales, finance]`, and no object is dropped.
- [ ] Given a manifest naming a dashboard, visualization or AI object id that does not exist in the
      parent tree, when validation runs, then it fails naming each unknown id and its manifest path
      (stale ids after a parent edit cannot rot silently).
- [ ] Given an entry under `unassigned:` whose `reason` is empty, whitespace, or one of the
      placeholder strings `TODO`, `TBD`, `n/a`, when `globalmart domains validate --strict` runs,
      then it fails naming that id — a deliberate exclusion must be justified in words.
- [ ] Given the parent's AI-context objects (`memoryItems`, parameters, agent personalities and AI
      knowledge — the four channels STEERING § Portability Contract requires to travel *and* be
      filtered per domain, selected by `ai.memory_item_ids` / `memory_item_tags` / `parameter_ids` /
      `agent_ids` / `knowledge_ids`), when validation runs, then every one is classified — assigned
      to at least one domain, declared `shared:`, or excluded with a reason — so that no unclassified
      AI object can leak into a child by default.
- [ ] Given a parent tree and no existing manifest, when `globalmart domains bootstrap` runs, then
      `config/domains.yaml` is generated by matching `viz_<domain>_` prefixes against the 12 known
      keys (longest key first, so `store_ops` beats `store`), a dashboard is assigned to **every**
      domain any of its tiles belongs to, and every object the generator could not classify lands
      under `unassigned:` with a `TODO:` reason rather than being omitted.
- [ ] Given an existing `config/domains.yaml`, when `globalmart domains bootstrap` runs without
      `--force`, then it refuses and exits 1 — the prefix convention may produce the file once, never
      overwrite a reviewed one.
- [ ] Given a generated manifest, when the generator is run twice into two paths, then the two files
      are byte-identical (domains sorted by key, every id list sorted lexically), and
      `load_domains(write(load_domains(f))) == load_domains(f)`.
- [ ] Given a grep of `src/globalmart/**/*.py` and `config/**` for the 12 domain keys or their
      labels, when the single-source test runs, then the only files containing the list are
      `config/domains.yaml` and the one-time `src/globalmart/domain_bootstrap.py` seed constant —
      nowhere else.
- [ ] Given the manifest, when a child workspace id and display name are resolved, then the id is
      `globalmart-<key with underscores replaced by hyphens>` (e.g. `globalmart-store-ops`) and the
      name is `workspace_name_template` applied to the label (default `GlobalMart — {label}`), both
      overridable per domain and both asserted unique across the 12.
- [ ] Given a domain carrying an optional `ldm_include:` list of dataset ids, when the manifest is
      loaded and validated, then those ids are exposed on `Domain.ldm_include` and every one of them
      must exist in the parent's `ldm.datasets` or validation fails naming the id and its manifest
      path; and `ldm_include` never counts as coverage of a dashboard, visualization or AI object —
      it is authoring headroom for the child's LDM only, not a membership declaration, and is
      reported separately from the `shared:` block.

## Scope

- `config/domains.yaml` — the committed manifest, sibling to `config/targets.yaml`.
- Its schema, versioned with a top-level `version: 1`, documented in `docs/domains.md`.
- `src/globalmart/domains.py` — `DomainManifest`, `Domain`, `AiSelection`, `Exclusion`,
  `SharedSelection`, `UnassignedSelection`, `load_domains(path) -> DomainManifest`,
  `dump_domains(manifest, path)`, `DomainManifestError(GlobalmartError)`, strict parsing that rejects
  unknown keys instead of ignoring them, plus the consumer accessors FEAT-004 reads the manifest
  through — `by_key()`, `keys()`, `resolve_workspace_name()` and `unassigned_ids()` — so no consumer
  re-derives a workspace name or flattens the exclusion lists itself. `Domain` also carries the
  optional `ldm_include` escape hatch — dataset ids a domain wants in its child's LDM beyond what
  FEAT-004's closure reaches, so there is room to author new metrics and visualizations in a child
  rather than only the ones today's dashboards happen to touch.
- `src/globalmart/coverage.py` — `check_coverage(model, manifest) -> CoverageReport` and the loud
  failure `CoverageError`. This is the enforcement STEERING demands.
- An extension to FEAT-002's `src/globalmart/traversal.py`: `iter_dashboard_insight_refs(model)`,
  the one enumeration of which visualizations a dashboard's layout references — needed to know which
  visualizations a listed dashboard already covers.
- `src/globalmart/domain_bootstrap.py` — the one-time generator, the only sanctioned place where the
  `viz_<domain>_` prefix and the 12 seed labels appear in code.
- CLI: `globalmart domains validate [--strict]` and `globalmart domains bootstrap [--dry-run]
  [--force]`, plus a human-readable coverage report (`--format table|json`).
- Offline tests against `tests/fixtures/mini_globalmart/` and a small set of deliberately broken
  manifests.
- A CI job running `globalmart domains validate --strict`, so a parent edit that orphans a dashboard
  fails the PR that made it.

## Out of Scope

- Splitting, transitive closure beyond dashboard → visualization, LDM pruning, and writing
  `generated/workspaces/globalmart-<domain>.json` — all FEAT-004. FEAT-003 stops at "which ids
  belong where, and is that complete".
- Publishing children (FEAT-004 via FEAT-002's `publish_workspace`).
- Deciding the *content* of the domains — the 12 keys and labels are inherited from the existing
  workspace and are seed data, not a design exercise in this feature.
- Repairing the parent: if the coverage check exposes eval-artifact visualizations or a genuinely
  orphaned dashboard, this feature records them as explicit exclusions with a reason; deleting them
  from the parent is a separate reviewable change.
- Per-domain data filtering or row-level security. Domains partition analytics and AI context, not
  rows.

## Key Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| The bootstrap's prefix guesses get committed unreviewed and the new manifest is just the old convention in YAML clothing — the exact flaw being designed out | High | High | Anything the generator cannot classify gets a `TODO:` reason, and `validate --strict` (the CI gate) fails on any `TODO:` reason, so an unreviewed manifest cannot go green |
| A large residue of the 384 visualizations turns out to be reachable from no dashboard and to match no prefix, and triaging it by hand is the real cost of the feature | High | Medium | The bootstrap prints the residue count before writing; the manifest supports a per-domain `visualizations:` list for real orphans and `unassigned:` for artifacts; triage is an explicit task, not a surprise |
| Coverage is enforced on ids only, so a dashboard can be "covered" while the visualization it embeds is assigned to a different domain, producing a child with a broken tile | Medium | High | `check_coverage` walks `iter_dashboard_insight_refs` and reports, per domain, any visualization referenced by a listed dashboard but not covered by that same domain; FEAT-004's closure fixes it by construction, but the report makes the split's shape visible here |
| `iter_dashboard_insight_refs` misses a widget shape (nested layouts, rich-text with embedded refs, drill targets), so coverage silently under-counts | Medium | High | The extractor walks the dashboard content dict generically for `{"identifier": {"id": ..., "type": "visualizationObject"}}` rather than assuming a section/column shape, and a test plants a ref in a nested layout and a drill definition |
| AI-context objects have no obvious per-domain signal at all, so the "no cross-domain memory" constraint is satisfied on paper by excluding everything | Medium | Medium | Deny-by-default is deliberate: an AI object reaches a child only if explicitly listed. The report prints how many memory items each domain received, so an all-zero column is visible rather than comfortable |
| The 12 seed labels live in `domain_bootstrap.py`, which is a second copy of domain truth — the very thing this feature exists to kill | Medium | Low | The single-source test allow-lists exactly that one module; a task deletes nothing but pins it, and the module docstring states it is one-time seed data that must not be read at runtime by anything else |
| The manifest and the parent drift apart between PRs (someone adds a dashboard, nobody adds it to a domain) | High | Medium | CI runs `validate --strict` on every PR; the failure names the new dashboard and points at `config/domains.yaml` |

## Dependencies

- **Depends on:** feat-001 and feat-002. From feat-001: `read_tree()`, the normalized parent tree,
  stable object ids, `GlobalmartError`. From feat-002: `traversal.py`, which this feature extends
  rather than duplicates, and `publish_workspace`'s `--workspace-name` parameter, which the
  manifest's resolved workspace name feeds. External: `PyYAML`, already a FEAT-001 dependency.
- **Enables:** feat-004. The splitter reads this manifest and nothing else for membership, reaching
  it only through `load_domains()`, `by_key()`, `keys()`, `resolve_workspace_name()` and
  `unassigned_ids()`; the `shared` block, the nested `ai` selection (including
  `memory_item_tags` and `knowledge_ids`) and the per-domain `ldm_include` list are part of that
  contract — FEAT-004 adds `ldm_include` datasets to its closure seed and reports them separately
  from the closure-reached ones. Indirectly this also enables
  feat-006, whose per-domain verification needs to know what each child should contain.
- **Note for the registry:** this spec's frontmatter carries `depends_on: []` / `enables: []`, which
  contradicts FEAT-001's `enables: [feat-003]` and ADR 001. The frontmatter is CLI-owned and is not
  edited here; the dependency edges above are the intended ones.

## Related Research

- ADR 001 — "Domain membership by `viz_<domain>_` id prefix (status quo)" is listed as a rejected
  alternative with the cons "mixed-domain dashboards silently dropped, no coverage guarantee". This
  feature is the acceptance of that rejection.
- STEERING § Architecture Constraints: "Domain membership is explicit — declared in `domains.yaml`,
  not inferred from object-id naming conventions. Prefix conventions may only be used to bootstrap
  that file once." And: "Coverage is enforced: every dashboard and visualization in the parent must
  land in at least one domain, or the split fails loudly."
- STEERING § Portability Contract: "The splitter still filters them per domain — cross-domain AI
  memory in a child is also a defect." That sentence is why the manifest carries an `ai:` block per
  domain rather than leaving AI context to FEAT-004.
- STEERING § Naming Conventions: child ids `globalmart-<domain>` in kebab-case; domain keys in
  `domains.yaml` in snake_case. The two spellings differ, which is why the mapping is a template in
  the manifest and asserted by a test rather than assumed.
- FEAT-002 breakdown resolved that the workspace display name travels with content, not with the
  target: `PARENT_WORKSPACE_NAME = "GlobalMart"` in `publish.py`, overridable with
  `--workspace-name`, and "FEAT-004 passes each child's label from `domains.yaml` (e.g.
  `"GlobalMart — Sales"`)". The manifest therefore stores the bare label (`Sales`) plus a
  `workspace_name_template` that renders it, so the published string and the human label are not
  conflated.
- Measured on the 2026-06-25 export: 32 analytical dashboards, 384 visualization objects, 1075
  metrics, 2713 descriptions. The 12 domains and their labels are taken from that export's
  predecessor split scripts.

## Open Questions

- ~~May a dashboard or visualization belong to more than one domain?~~ **Resolved: yes,
  many-to-many.** Coverage requires *at least* one domain, never exactly one. A mixed-domain
  dashboard is listed under every domain it serves and is copied into each child; children are
  separate workspaces, so duplicate ids never collide. Enforcing exclusivity would recreate the
  predecessor's drop-on-ambiguity behaviour with a better error message, which is not the point.
- ~~Where does the manifest live?~~ **Resolved: `config/domains.yaml`**, beside `config/targets.yaml`.
  STEERING names it `domains.yaml` without a directory and explicitly exempts it (with config) from
  the no-hardcoded-identifiers rule, which is the same exemption `config/` already carries.
- ~~Do visualizations reachable from a listed dashboard need to be listed too?~~ **Resolved: no.**
  A dashboard covers the visualizations its layout references, computed by
  `iter_dashboard_insight_refs`. The per-domain `visualizations:` list exists only for visualizations
  that belong to a domain but sit on no dashboard.
- ~~How is AI context scoped?~~ **Resolved: deny-by-default.** A memory item, parameter or agent
  personality reaches a child only if that domain lists it, or if it is declared `shared:`. Nothing
  is inherited implicitly, because the failure mode STEERING names is leakage, not absence.
- **Open — needs the bootstrap run to answer:** how many of the 384 visualizations are reachable from
  no dashboard and match no prefix, and are they real content that needs a domain or eval artifacts
  that should be excluded? The manifest expresses both outcomes; which one applies is a judgement
  call on the actual residue and is called out as a `[DECISION NEEDED]` in the task list.
- ~~Should `shared:` exist at all, or is "in every domain" always a modelling smell? If the reviewed
  manifest ends up with an empty `shared:` block it should be deleted from the schema in FEAT-004.~~
  **Resolved 2026-09-18: `shared:` stays, empty or not.** FEAT-004 now carries AC #17 asserting
  shared objects reach every child, and its fixture manifest exercises the block by construction.
  An empty `shared:` is valid and costs nothing; removing the surface later would be a schema
  migration plus a splitter change, and re-adding it when the first genuinely cross-domain parameter
  appears would cost more than leaving it. Listing one id under 12 keys remains the worse option.
- **Open:** may an object be listed under both `shared.ai` and a domain's own `ai`? Union semantics
  make this harmless and idempotent, and `CoverageReport.multi_homed` already reports it — proposed
  resolution is to allow it and never error, but state it explicitly in the validator's rules so a
  reviewer is not left guessing whether a double listing is a mistake.
